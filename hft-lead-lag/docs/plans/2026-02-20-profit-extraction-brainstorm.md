# Profit Extraction Brainstorm (Draft)

**Date:** 2026-02-20  
**Status:** Draft (analysis only, no code changes in strategy logic yet)

## 1) Зачем этот документ

Зафиксировать рабочие выводы по текущему runtime и оформить гипотезы для перехода от paper-статистики к более устойчивому извлечению прибыли.

## 2) Текущее состояние (snapshot)

- Код и документация полностью просмотрены.
- Runtime endpoint `/health` отвечает `ok` (Binance/Gate connected).
- В `data/optimizer.db`:
  - `configs`: 2304
  - `trades`: 16977
  - global PnL: отрицательный (средний трейд около `-0.042%`)
  - активность сильно неравномерна по символам
- Покрытие grid:
  - сделки есть только у `gap=30`
  - `gap=50/60/80` фактически не участвуют
- Реально edge концентрируется на малом числе инструментов и не переносится между монетами.

## 3) Как работает текущая модель

Текущая логика в `shadow_trader`:

- вход по сигналу `current_gap - baseline_gap >= spike_threshold_bps`
- baseline считается по `baseline_window_ms`
- выход двухфазный:
  - до breakeven: `stop_loss`/`timeout`
  - после breakeven: `breakeven` и `trailing_take`

Это логика "spike follow" с baseline-нормализацией, а не чистая mean-reversion.

## 4) Ключевая проблема

Даже при рабочем pipeline (`WS -> screener -> fleet -> DB -> ranking`) нет адаптивного policy-слоя:

- нет онлайн-переключения конфига по символу и режиму;
- отбор в основном делается постфактум ranking-эндпоинтами;
- конфиги быстро "стареют" при смене режима рынка.

## 5) Гипотеза пользователя: percentile reversion

Формулировка:

- вход на раскоре `bid/ask` в зоне `P90`, выход на `P50`;
- в обратную сторону вход от `P10`, выход на `P50`.

Это естественно трактуется как **percentile-based mean reversion**.

### 5.0 Уточнение semantics (2026-02-20)

По уточнению пользователя это не "жесткий контртренд", а:

- **сведение/прилипание к Binance** как к более сильному reference venue;
- гибридная логика, сочетающая:
  - mean-reversion по раскору,
  - momentum на раскорреляции (когда режим ускоряется);
- вход возможен при уходе за `P90` даже если событие вызвано не только движением Binance, а совокупной динамикой пары Binance/Gate.

Итого: рабочее название гипотезы — **Binance Anchored Percentile Convergence**.

### 5.1 Формализация (вариант)

Для LONG-reversion:

- `spread_long_bps = (binance_ask - gate_ask) / gate_ask * 10000`
- вход, когда `spread_long_bps >= P90(spread_long_bps, W)`
- выход, когда `spread_long_bps <= P50(spread_long_bps, W)`

Для SHORT-reversion:

- `spread_short_bps = (gate_bid - binance_bid) / gate_bid * 10000`
- вход, когда `spread_short_bps <= P10(spread_short_bps, W)` или симметрично через знак
- выход, когда `spread_short_bps >= P50(spread_short_bps, W)`

Где `W` — rolling окно (например 10s/20s/30s/60s), отдельно по символу.

### 5.2 Чем это отличается от текущей модели

- Сейчас: fixed threshold на baseline-adjusted сигнал.
- В новой гипотезе: динамический threshold как квантиль текущего режима.

Это как раз то, чего сейчас не хватает: адаптация к regime shift без ручного retune.

### 5.3 Дополнительная метрика: время в экстремальной зоне

Пользовательская идея: считать **время нахождения сигнала за `P90`/`P10`** как метрику качества входа.

В документе фиксируем как:

- `time_above_p90_ms` (или `time_below_p10_ms`) — длительность непрерывного пребывания в экстремальной зоне;
- **жесткий gate на вход:** `time_above_p90_ms >= p90_ping_ms` (для верхнего экстремума) и
  `time_below_p10_ms >= p90_ping_ms` (для нижнего экстремума);
- это может использоваться как:
  - фильтр ложных всплесков (минимальное dwell-time),
  - и как "decision window" для бота (дедлайн на вход/отказ от входа).

Практический смысл:

- короткие одиночные выбросы чаще шум;
- устойчивое нахождение в экстремуме чаще означает структурный дисбаланс и более валидный сигнал.

### 5.4 Временный operational default

До калибровки по live latency в качестве рабочего дефолта фиксируем:

- `p90_ping_ms = 50`

Это именно временный baseline для экспериментов, затем заменить на адаптивную метрику.

### 5.5 Entry state-machine (предложение)

Для каждого символа вести автомат:

1. `Neutral`
2. `ExtremeTracking`
3. `Armed`
4. `InPosition`
5. `Cooldown`

Переходы:

- `Neutral -> ExtremeTracking`:
  - `spread_long_bps >= P90` или `spread_short_bps <= P10`
- `ExtremeTracking -> Armed`:
  - dwell-time в экстремуме достиг `>= 50ms`
  - quote freshness и spread-фильтр валидны
- `Armed -> InPosition`:
  - подтверждение на следующем тике (анти-спайк)
  - вход по текущей модели fill-delay
- `InPosition -> Cooldown`:
  - выход по правилам (см. ниже)
- `Cooldown -> Neutral`:
  - истек cooldown

Зачем это нужно:

- исключает вход на одиночном шумовом тике,
- делает правило понятным и наблюдаемым в телеметрии.

### 5.6 Exit логика для percentile-модели (предложение)

Базовый вариант:

- LONG: выход, когда `spread_long_bps <= P50`
- SHORT: выход, когда `spread_short_bps >= P50`

Guardrails (обязательные):

- hard stop loss (в bps по фактической позиции на Gate)
- max hold timeout
- принудительный exit при деградации quote freshness

Опционально:

- частичный выход на `P60/P40`, полный на `P50` (если потребуется уменьшать tail-risk).

### 5.7 Что можно считать momentum в этой логике

Чтобы модель оставалась "сведение к Binance", но учитывала persistence:

- вход разрешается только если экстремум не схлопнулся мгновенно;
- длительность в экстремуме (`time_above_p90_ms`) трактуется как сила/устойчивость дисбаланса;
- чем дольше удержание экстремума, тем выше приоритет входа (в продвинутой версии policy).

Это и есть гибрид: не чистый reversion, а reversion c фильтром устойчивости импульса.

## 6) Риски percentile-reversion

- На трендовом импульсе reversion вход может быть преждевременным (ловля "убегающего поезда").
- P50-выход может быть слишком "оптимистичным" при слабой конвергенции.
- Нужны жесткие guardrails:
  - max hold
  - stop loss
  - cooldown
  - freshness checks
  - spread/liquidity фильтр

## 7) Практичный путь внедрения

Не заменять текущую модель сразу, а добавить вторую стратегию в Shadow Fleet:

1. `Model A`: текущий baseline spike-follow (как есть)
2. `Model B`: percentile-reversion (`P90/P10 -> P50`)
3. Сравнение только на out-of-sample rolling окне по символам
4. Policy-manager выбирает активный профиль по symbol/regime

## 8) Минимальный эксперимент для проверки гипотезы

- Добавить в shadow новую ветку entry/exit на перцентилях.
- Прогнать минимум 24-72 часа в live paper.
- Сравнивать:
  - avg pnl/trade
  - hit rate
  - max adverse excursion proxy
  - стабильность по квартилям времени
  - переносимость между символами

Критерий прохождения:

- не просто высокий avg pnl на одном символе,
- а положительное ожидание на группе символов и меньшая деградация при смене режима.

## 9) Предварительная инженерная рекомендация

Лучший следующий шаг: **гибрид**.

- Использовать percentile-reversion как отдельный режим (или отдельный policy branch),
- не выбрасывая spike-follow,
- и добавить runtime policy-selection (какой режим активен для символа сейчас).

## 10) Варианты стратегии (понакидать)

### Вариант A: Strict Percentile Convergence (консервативный)

- Вход только по `P90/P10 + dwell>=50ms`.
- Выход строго на `P50`.
- Жесткие stop/timeout/cooldown.

Плюсы:

- простая интерпретация и отладка;
- быстро проверить гипотезу.

Минусы:

- может пропускать хорошие "быстрые" сигналы;
- в некоторых режимах будет низкая частота сделок.

### Вариант B: Convergence + Persistence Weight (базовый рекомендованный)

- База как в варианте A.
- Добавляется score входа:
  - `score = f(extreme_distance, dwell_time, freshness, spread_cost)`
- Вход только если `score >= threshold`.

Плюсы:

- лучше отсекает слабые сигналы;
- дает путь к runtime policy-менеджеру.

Минусы:

- больше гиперпараметров;
- сложнее explainability, чем у A.

### Вариант C: Dual-Mode (Convergence/Momentum switch)

- Два режима на одном сигнале:
  - `Mode C`: сведение к `P50`
  - `Mode M`: continuation с более поздним выходом (например через trailing или квантильный канал)
- Переключение по regime-признакам:
  - dwell-time
  - скорость изменения spread
  - локальная волатильность

Плюсы:

- потенциально лучший захват разных рыночных фаз.

Минусы:

- максимальная сложность и риск переобучения;
- не подходит как первый production шаг.

## 14) Модульность стратегий без фабрики

Задача:

- уметь выбирать стратегию в runtime;
- добавлять новую стратегию с минимальным количеством правок;
- не строить отдельную factory-иерархию.

### 14.1 Рекомендуемый паттерн: enum-dispatch + общий engine

Идея:

- `ShadowTrader` остается execution-engine (позиция, fill-delay, pnl, cooldown, guardrails);
- сигнал и правила выхода выносятся в отдельные strategy-модули;
- выбор стратегии делается через enum в конфиге.

Пример структуры:

- `src/domain/screener/strategies/mod.rs`
- `src/domain/screener/strategies/baseline_gap.rs`
- `src/domain/screener/strategies/percentile_convergence.rs`

Ключевые типы:

- `StrategyKind` (enum): `BaselineGap`, `PercentileConvergence`, ...
- `StrategyState` (enum/struct): локальное состояние конкретной стратегии
- `StrategyDecision`: `Noop | Enter(Long/Short, reason) | Exit(reason)`

Диспетчер:

- в `ShadowTrader::tick()` один `match strategy_kind` и вызов соответствующего модуля.

Почему это лучше сейчас:

- без factory и без сложной динамики trait-объектов;
- compile-time понятность;
- добавление стратегии = новый файл + новая ветка enum/match.

### 14.2 Где хранить выбор стратегии

Минимально:

- добавить `strategy_kind` в `TraderConfig`;
- включить `strategy_kind` в `config_id()`;
- добавить поле в БД `configs.strategy_kind`;
- вернуть поле в `/api/v1/fleet*` endpoints.

Тогда fleet может одновременно гонять несколько типов стратегий.

### 14.3 Контракт стратегии (минимальный)

Стратегия должна отвечать только за alpha-логику:

- как посчитать signal;
- когда дать `Enter`;
- когда дать `Exit`.

Engine отвечает за:

- order simulation;
- fees/pnl;
- stop/timeout/cooldown;
- trade lifecycle и статистику.

Это ключевое разделение, чтобы не размазывать логику по проекту.

### 14.4 Как добавить новую стратегию “дешево”

Чеклист:

1. Создать новый модуль в `strategies/`.
2. Реализовать функции `on_tick_entry`/`on_tick_exit` под общий контракт.
3. Добавить variant в `StrategyKind`.
4. Добавить ветку в один `match` диспетчера.
5. Добавить default-параметры в `TraderConfig` (если нужны).
6. Добавить 3-5 unit-тестов только на signal/exit модуля.

На этом всё. Остальной engine и API трогать минимально.

### 14.5 Альтернатива (если захотите ещё чище позже)

Позже можно перейти на trait-based pluggable strategies, но на текущем этапе enum-dispatch проще в сопровождении и быстрее в доставке.

## 16) Почему модульность сократит время разработки (с обоснованием)

### 16.1 Текущий shape кода (факт)

Размеры ключевых файлов:

- `src/domain/screener/shadow_trader.rs`: `944` LOC
- `src/main.rs`: `1081` LOC
- `src/api/handlers.rs`: `438` LOC
- `src/domain/screener/shadow_fleet.rs`: `217` LOC
- `src/infrastructure/db.rs`: `241` LOC

Это означает, что alpha-правки сейчас быстро затрагивают engine/db/api одновременно.

### 16.2 Исторический пример cross-layer изменений

Даже одно расширение (`baseline_window_ms`) потребовало правки:

- `TraderConfig`
- grid generation
- DB schema/migrations/upsert
- API endpoints `/fleet*`
- ranking payloads

Вывод:

- без модульного контракта каждая новая идея тянет широкий change-surface.

### 16.3 Change-surface до/после enum-dispatch

До (сильная связанность):

- типично `6-10` файлов на новую стратегию (`shadow_trader`, `fleet`, `config`, `db`, `api`, тесты)

После (предложенный паттерн):

- типично `2-4` файлов:
  - новый модуль в `strategies/`
  - 1 `enum` variant + `match` ветка
  - минимум конфиг/тест

Практический эффект:

- быстрее итерации гипотез;
- меньше риск регрессий в execution-engine;
- проще rollback на уровне `strategy_kind`.

## 17) Оценка сроков (зафиксировано)

### 17.1 Внедрение percentile-стратегии

- быстрый прототип (`P90/P10 -> P50`, `dwell=50ms`, без policy-manager):
  - ориентир: `6-10 часов`
- рабочий shadow-вариант (тесты, метрики, API-поля):
  - ориентир: `2-3 рабочих дня`
- полноценный adaptive runtime selection:
  - ориентир: `5-8 рабочих дней` + `24-72 часа` paper-наблюдения

### 17.2 Эффект от модульности без фабрики

- разовая инвестиция в enum-dispatch модульность:
  - ориентир: `6-10 часов`
- после этого добавление новой стратегии:
  - ориентир: `2-4 часа` вместо `1-2 дней` в текущей связанной схеме

Вывод:

- если ожидается более одной новой стратегии, модульность экономически оправдана.
