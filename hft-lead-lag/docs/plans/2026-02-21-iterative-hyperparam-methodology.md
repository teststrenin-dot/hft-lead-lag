# Iterative Hyperparameter Discovery Methodology (<=1600 configs/run)

**Goal:** перейти от состояния "ничего не известно" к устойчивому пониманию рабочих/мертвых зон гиперпараметров без полного перебора и без случайного поиска.

**Scope:** shadow-fleet deal-hunt цикл с hot-reload, выгрузкой результатов в БД и итеративным пересбором диапазонов/шагов.

---

## 1. Ограничения и принципы

1. Лимит на один запуск: `N <= 1600` конфигов.
2. Нельзя:
   - тупой полный перебор;
   - random search.
3. Нужно:
   - детерминированный выбор следующего батча;
   - явные правила "расширять/сужать диапазон";
   - явные правила "уменьшать/увеличивать шаг";
   - раннее выключение dead-end областей;
   - периодический canary-recheck dead-end для защиты от regime shift.

---

## 2. Целевые метрики (фаза поиска сделок)

Для каждого `config_id` и `run_id` считаем:

1. `trades_count`
2. `ultra_churn_count` = `early_stop_churn = 1` (stop_loss и `hold_ms <= 500`)
3. `ultra_churn_share` = `ultra_churn_count / max(1, trades_count)`
4. `natr_q50`, `natr_q90` по сделкам конфига
5. `coverage_symbols` (сколько символов дали хотя бы 1 сделку)

На первой фазе главная цель: **найти зоны, где вообще есть сделки**, при этом отсечь "ультраговно".

---

## 3. Представление пространства параметров

Каждый гиперпараметр хранится как ось с интервалами (bins):

1. `gap_threshold_bps`
2. `target_ratio`
3. `stop_loss_bps`
4. `max_hold_ms`
5. `max_spread_bps`
6. `trailing_decay_ratio`
7. `baseline_window_ms`

Для каждой оси ведем таблицу статуса интервалов:

1. `unknown`
2. `alive`
3. `dead`
4. `quarantine` (есть сделки, но слишком высокий `ultra_churn_share`)

---

## 4. Итерационный цикл (один run)

`run_duration`: 10 минут (для быстрых итераций), затем пересчет и hot-reload.

### Шаг 1: Агрегация run-статистики

Собираем из БД статистику `config_id x run_id`, плюс срезы по NATR-квантилям.

### Шаг 2: Классификация конфигов

1. `dead-hard`:
   - `trades_count = 0` в `R_dead` подряд runs (рекомендация: `R_dead = 2`).
2. `dead-soft (quarantine)`:
   - `trades_count >= min_trades_soft` (например `20`) и
   - `ultra_churn_share >= 0.85`.
3. `alive`:
   - `trades_count > 0` и не попал в `quarantine`.

### Шаг 3: Обновление диапазонов и шага по каждой оси

Для соседних точек `v_i`, `v_{i+1}` считаем:

1. `rate_i = trades_count_i / run_minutes`
2. `slope_i = rate_{i+1} - rate_i`
3. `risk_i = ultra_churn_share_i`

Правила:

1. **Split (шаг уменьшить в 2 раза)**:
   - если рядом переход `dead -> alive`;
   - или `|slope_i|` выше порога (`eps_split`);
   - или высокая неопределенность (мало наблюдений, но есть сделки).
2. **Merge (шаг увеличить в 2 раза)**:
   - если `|slope_i| < eps_flat` и `risk` стабилен `K_flat` циклов.
3. **Expand range (расширить край)**:
   - крайняя точка `alive` и `slope_edge` направлен "наружу";
   - `risk_edge` ниже лимита.
4. **Shrink range (сжать край)**:
   - край и соседняя точка `dead-hard` `K_shrink` циклов подряд.

### Шаг 4: Формирование следующего батча (<=1600)

Бюджет делится фиксированно и детерминированно:

1. `Control` (100): стабильные контрольные конфиги для drift-мониторинга.
2. `Frontier` (550): новые точки в зонах `unknown` и на границах `alive/dead`.
3. `Refine` (600): локальное уплотнение шага (split-зоны).
4. `Boundary` (250): проверки на расширение диапазонов.
5. `Canary` (100): редкая проверка `dead/quarantine` зон.

Итог: `100 + 550 + 600 + 250 + 100 = 1600`.

Отбор внутри корзин:

1. по score (детерминированно);
2. tie-break по лексикографическому порядку tuple параметров;
3. никакого случайного выбора.

---

## 5. Score-функция (без PnL на первой фазе)

Для этапа "поиск живых зон" используем:

`score_presence = w1 * norm(trades_count) - w2 * ultra_churn_share + w3 * uncertainty_bonus + w4 * boundary_bonus`

Где:

1. `uncertainty_bonus` высокий у малоизученных зон;
2. `boundary_bonus` высокий у краев, где возможно расширение;
3. веса фиксируются в конфиге и меняются только через hot-reload policy.

---

## 6. Как именно выходим из "ничего неизвестно"

### Stage A: Bootstrap Mapping (2-4 runs)

1. Старт с грубых осей (крупный шаг).
2. 70% бюджета на `unknown`, 20% на boundary, 10% controls.
3. Задача: быстро отделить `dead-hard` от потенциально `alive`.

### Stage B: Frontier Consolidation (4-10 runs)

1. Убираем `dead-hard` из основного батча.
2. Вокруг переходов `dead/alive` режем шаг (split).
3. Края с живым трендом расширяем на 1-2 шага.
4. Canary на dead-зоны оставляем (5-10%).

### Stage C: Interaction Discovery (6-12 runs)

1. Берем top-3/top-4 самых чувствительных параметра (по величине изменения `trades_count`).
2. Строим детерминированные 2D/3D срезы только в alive/near-frontier областях.
3. Отсекаем оси с минимальным вкладом (irrelevant на этой фазе).

### Stage D: Regime-Aware Mapping via NATR (6+ runs)

1. Разбиваем данные по `NATR` бинам (например, low/mid/high volatility).
2. Повторяем frontier/refine логику внутри каждого NATR-режима.
3. Получаем режимные рекомендации (одни параметры для low-NATR, другие для high-NATR).

---

## 7. Dead-end политика

1. `dead-hard`:
   - выключается из основного прогона;
   - остается только в `canary`.
2. `quarantine`:
   - временно исключается из основного прогона;
   - возвращается только если в canary `ultra_churn_share` упал ниже порога.
3. "Возврат из dead":
   - минимум 2 успешных canary-run подряд.

---

## 8. Критерии "полного понимания" гиперпараметров

Считаем фазу завершенной, когда:

1. Для каждой оси нет расширения диапазона `>= 3` циклов подряд.
2. Для каждой оси frontier-зоны покрыты наблюдениями выше `min_samples_axis`.
3. Доля resurrected dead-end (dead -> alive в canary) < 5%.
4. Рейтинг чувствительности параметров стабилен `>= 3` цикла.
5. Доля truly-unknown точек в рабочем диапазоне < 10%.

---

## 9. Что делаем дальше после этой фазы

1. Включаем PnL/стабильность как вторичную оптимизацию на уже найденных alive-зонах.
2. Переходим от статичных параметров к динамическим (например, `stop_loss = f(NATR)`).
3. Запускаем более длинные прогоны для подтверждения устойчивости.

---

## 10. Реализация в системе (практически)

1. Добавить `run_id` контур и таблицу сводной run-статистики по `config_id`.
2. Вынести policy выбора следующего батча в отдельный модуль (`planner`).
3. Каждые 5-10 минут:
   - пересчитывать классификацию (`alive/dead/quarantine/unknown`);
   - пересобирать runtime-grid;
   - применять через hot-reload.
4. Логировать решения policy (почему точка выключена/расширена/разбита по шагу).

---

## 11. Большой цикл действий (что обсуждали ранее, в одном контуре)

Ниже полный последовательный цикл от текущей точки до финальной фазы.

### Фаза 0: Фундамент данных и управления (уже сделано)

1. Горячая подмена runtime-grid через `config/runtime-grid.toml`.
2. Слив результатов прогона в БД.
3. Запись контекста сделки:
   - `gate_natr_30m_pct_at_entry`
   - `hold_ms`
   - `early_stop_churn` (ультраговно при `hold_ms <= 500` и `stop_loss`).

**Выход фазы:** система уже поддерживает короткие итерации с hot-reload и полной персистентностью результатов.

### Фаза 1: Массовый сбор "где вообще есть сделки" (текущая активная)

1. Короткие прогоны по 10 минут.
2. Ограничение `<=1600` конфигов на запуск.
3. Первичный фильтр:
   - вырезаем только `dead-hard` (сделок нет);
   - `quarantine` для зон с экстремальным `ultra_churn_share`.
4. Каждые 5-10 минут пересчет и hot-reload нового батча.

**Выход фазы:** карта alive/dead/quarantine по всем осям и frontier-области, где нужно резать шаг.

### Фаза 2: Титрация диапазонов и шага (адаптивное уплотнение)

1. Уплотняем шаг на переходах `dead/alive`.
2. Расширяем диапазон на "живых" краях.
3. Сужаем диапазон на устойчиво мертвых краях.
4. Оставляем canary-переоценку dead-end для защиты от смены режима.

**Выход фазы:** рабочий диапазон по каждому гиперпараметру, где неизвестность минимальна.

### Фаза 3: Обогащение большой таблицы и выявление взаимодействий

1. Накопление run-истории в едином контуре (`run_id`, срезы по конфигам).
2. Детерминированные 2D/3D срезы для top-чувствительных параметров.
3. Исключение осей с низким вкладом на данной фазе (нерелевантные настройки).

**Выход фазы:** понятные зоны взаимодействий параметров без глобального комбинаторного взрыва.

### Фаза 4: Динамические гиперпараметры от режима рынка (NATR-aware)

1. Делим среду на режимы по NATR (low/mid/high).
2. Строим функции параметров от режима:
   - например, `stop_loss_bps = f(NATR_bin)`,
   - при необходимости `target_ratio = g(NATR_bin)`.
3. Валидируем стабильность режима на коротких и средних прогонах.

**Выход фазы:** не один "магический" статичный набор, а режимная политика параметров.

### Фаза 5: Полный проход по релевантной области (финальный)

1. Запуск длинных прогонов только в подтвержденной релевантной области.
2. Контроль drift через control/canary корзины.
3. Финальный рейтинг конфигураций/политик по устойчивости и полезности.

**Выход фазы:** production-ready набор политик и список зон, которые исключены как dead-end.

### Фаза 6: Эксплуатационный цикл (непрерывная адаптация)

1. Периодический re-fit диапазонов и шага по той же методологии.
2. Авто-ревизия dead-end с canary-проверками.
3. Плановые пересборки динамических функций от NATR при накоплении новой статистики.

**Выход фазы:** замкнутый контур "прогон -> анализ -> hot-reload -> следующий прогон" без ручного перебора.

---

## 12. Контрольные точки перехода между фазами

Переход разрешен только при выполнении критериев:

1. `Фаза 1 -> Фаза 2`:
   - доля `unknown` заметно падает;
   - `dead-hard` стабилизированы минимум на `R_dead` циклах.
2. `Фаза 2 -> Фаза 3`:
   - нет агрессивного расширения диапазона `>=3` циклов подряд;
   - frontier покрыт минимальным числом наблюдений.
3. `Фаза 3 -> Фаза 4`:
   - выделены чувствительные оси и взаимодействия;
   - нерелевантные оси временно исключены.
4. `Фаза 4 -> Фаза 5`:
   - динамические правила от NATR показывают устойчивость на валидационных прогонах.
5. `Фаза 5 -> Фаза 6`:
   - есть стабильный shortlist production-кандидатов;
   - контроль drift/canary интегрирован в постоянный цикл.
