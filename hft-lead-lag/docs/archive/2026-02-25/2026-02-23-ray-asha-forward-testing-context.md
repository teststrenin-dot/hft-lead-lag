# Контекст на передачу: Forward Testing Shadow Fleet (Ray Tune + ASHA)

**Дата:** 2026-02-23  
**Статус:** зафиксировано, принять как базовый вариант  
**Цель документа:** передать единый контекст по выбранной архитектуре параллельного форвард-тестинга для теневой флотилии.

## 1) Зафиксированные решения
1. Оркестратор экспериментов: `Ray Tune`.
2. Планировщик и раннее отсечение: `ASHA` (`Asynchronous Successive Halving`).
3. Исполнитель торговой логики: `Rust worker` (горячий путь без аллокаций/копий).
4. Поиск делаем не последовательным: целевой масштаб `>2000` конфигов параллельно.
5. Собственный оркестратор не делаем (стоимость разработки/поддержки выше выгоды).
6. `Optuna` не используется как рантайм-исполнитель флота; допускается только как внешний sampler при необходимости.

## 2) Бизнес-задача (входные требования)
1. Сначала автоматически найти любые рабочие диапазоны, где вообще есть сделки (`scout`).
2. Затем умно расширять диапазоны, пока это дает сделки/сигнал, без бессмысленного ухода в бесконечность.
3. Пример жесткой границы: `stop_loss` расширяем только в заранее заданном коридоре (например, `0.1..0.5`), не выше.
4. После отбора лучшие конфиги должны подменяться в боевую конфигурацию без остановки процесса.

## 4) Целевая архитектура (Ray + Rust)
1. `Ray Driver` (control plane):
   - создает/управляет trial-ами;
   - назначает ресурсы (`CPU`) и concurrency;
   - применяет `ASHA` для раннего отсечения слабых конфигов.
2. `Rust Worker` (execution plane):
   - получает батч конфигов;
   - считает метрики на live/forward окне;
   - возвращает промежуточные и финальные результаты без лишних копий.
3. `Results Store`:
   - агрегированные метрики trial-ов;
   - экспорт топ-кандидатов для runtime-grid/hot-reload.
4. `Promotion Bridge`:
   - формирует обновленный набор конфигов;
   - применяет через существующий `replace_fleet_configs`.

## 5) Логика фазы поиска (обязательная)
1. `Scout phase`:
   - широкий, но конечный bounded sampling по всем параметрам;
   - primary objective: `trades_count`;
   - secondary guardrails: отсев мусорных конфигов (например, churn/stop-loss noise).
2. `Expand phase`:
   - расширяем только возле ячеек, где есть сделки/устойчивый сигнал;
   - расширение только внутри hard-bounds каждого параметра;
   - в мертвых зонах диапазон сужается или замораживается.
3. `Forward-test phase`:
   - ASHA ранжирует конфиги по ступеням бюджета (короткое/среднее/длинное окно);
   - конфиги без прогресса режутся рано.
4. `Promote phase`:
   - топ-N стабильных конфигов переводятся в runtime-grid и подхватываются hot-reload контуром.

## 6) Контракты по диапазонам (чтобы не было бесконечного расширения)
Для каждого параметра задается:
1. `hard_min`, `hard_max`
2. `init_min`, `init_max`
3. `step`
4. `expand_step`
5. `max_expands`

Минимальный инвариант:
1. Ни один параметр не может выйти за `hard_min..hard_max`.
2. Если на границе нет прироста по целевой функции, расширение прекращается.

## 7) Требования к производительности
1. Поддержка `>2000` параллельных конфигов через Ray scheduling + батчевый Rust execution.
2. Горячий путь: без лишних аллокаций и копий (`zero alloc`, `zero copy` по возможности).
3. Никаких блокирующих операций в критическом тиковом контуре.
4. Логи централизованы и сейчас выключены: это не блокер, не включаем в scope.

## 8) Non-goals на текущий этап
1. Не строим новый кастомный оркестратор поверх Ray.
2. Не делаем полную перестройку всего Screener/Shadow Fleet.
3. Не включаем real-money execution в этот этап.

## 9) Критерии готовности (Definition of Done для первой версии)
